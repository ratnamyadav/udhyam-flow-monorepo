# Passwordless email sign-in — 2 October 2026

Web, admin and Expo signup/login now use email + a six-digit code. Public guest booking still needs no login. Google remains optional when both provider credentials are configured. Legacy password/reset/verification pages redirect to email sign-in; old password endpoints are disabled. This is a source implementation, not a production rollout.

## Framework and controls

BetterAuth 1.7.7 `emailOTP`/`emailOTPClient` supports sign-in and automatic signup after proof, hashed OTP storage, constant-time hash comparison, and atomic verification. The installed Postgres Drizzle adapter consumes with `DELETE ... RETURNING`; verification is gated on the returned row, not a read followed by an unguarded deletion. See https://www.better-auth.com/docs/plugins/email-otp and the pinned installed source under `dist/plugins/email-otp` / `@better-auth/drizzle-adapter`.

- Cryptographically generated 6 digits via Node `randomInt`, including leading zeros; framework `storeOTP: 'hashed'` (SHA-256) stores the digest + attempt count, never the code. Codes live briefly in memory to send the email, and in isolated test mail capture; neither is logged.
- Five-minute expiry, single successful consumption, five wrong attempts per challenge; the sixth verification fails even if correct. No generic public check-code oracle is permitted.
- Sixty-second persistent recipient resend cooldown. Resend deletes all earlier sign-in challenges, then creates a fresh code. Delivery failure fails closed; it does not fall back to console printing codes.
- Persistent recipient budgets: 3 sends and 15 verification attempts per 15-minute window across challenges/devices. Persistent IP budgets: 20 sends and 60 verifications per 15 minutes across recipients. These atomic Postgres UPSERTs reuse the existing verification table's deterministic primary key and store hashed identifiers/counts. They work across processes and require no new OTP schema migration.
- IP guards accept only the explicitly configured `TRUSTED_IP_HEADER` supplied/overwritten by the edge. Without it, all unattributed clients share a conservative fallback budget; an untrusted forwarded header cannot bypass the database limits. Configure and verify this header before deployment. BetterAuth also applies its supported 5/minute per-route limiter in production; the persistent guards do not depend on its in-memory state.
- Email is trimmed/lowercased on client and server. Existing BetterAuth creation already lowercases addresses. Imported legacy addresses/case collisions still require a deployment data audit, not a silent bulk rewrite.
- Known/unknown addresses receive identical successful send responses and both receive a sign-in code, since verified signup is allowed. Names/roles are not disclosed before proof. UI errors are generic, without raw provider/database messages. No new admin/owner privilege is granted by code entry; role remains non-input `user`, while existing membership/role gates apply.
- One text code field supports paste, numeric input, browser/native autofill, labels/live status, resend countdown, change-email/back recovery and keyboard-safe mobile layout. Code is held in component memory and cleared on success/back; not stored in URLs or local storage.

## Existing accounts and sensitive actions

Existing verified users keep their IDs, names, credential records, memberships and standing sessions. Successful OTP creates an additional normal BetterAuth session, with the oldest workspace selected through the existing hook. It does not create a replacement account or rewrite passwords.

For an existing *unverified* email, BetterAuth's supported promotion revokes unproven credential/OAuth links and sessions before marking it verified and issuing the mailbox owner's session. The user ID and business memberships remain. This is tested and deliberately avoids inheriting a password/session created before mailbox control was proved.

Deletion remains a separate fresh, purpose-bound email link requested from an authenticated session, with ownership checks at execution. A login/signup code does not authorize deletion. The code guard disables unrelated OTP verification, password-reset and email-change endpoints. Existing Google linking/tenant/admin checks are preserved. No production account was deleted or changed.
